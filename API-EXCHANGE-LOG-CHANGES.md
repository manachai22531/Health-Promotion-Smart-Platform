# Operations API Request / Response

Adds a tab after Production Readiness, using the original Operations theme. It lists insertion time, source (application API or configured HIS HTTP call), operation, method, HTTP status, independent business/transport outcome, duration and actor. Filters cover Thai-calendar date ranges, operation name, source and Success/Error, with 50-row pagination and actual totals. Detail shows masked JSON request/response, copy buttons and correlation to other entries with the same request ID. Both apiView and auditView are required on the server and client.

Application requests under /api are recorded after completion/abort; authentication/session routes, performance ingestion and the log viewer's own routes are excluded. File/binary or precompressed replies record metadata rather than binary content. Configuration, credentials, full-state, import/upload and SQL administration endpoints omit bodies. Other payloads have credential and common patient/clinical fields redacted before queueing; JSON strings are parsed and sanitized too, malformed/oversized JSON strings omitted. Headers, cookies, complete URLs and API keys are never captured. Payloads are bounded, array depth/size limited and truncation indicated. This is a diagnostic view, not a replacement for existing workflow/security audit logs.

Configured HIS calls through callConfiguredHisJson record a logical call's final outcome including any existing GET_VISIT retries. The existing retry/send policies are unchanged. Non-2xx transport errors carry non-enumerable HTTP/response metadata for logging without changing existing error messages or serialization. HTTP 200 with explicit ok/success/status failure is BUSINESS_ERROR; HTTP failure, timeout, network failure and abort have separate types. Calls made outside this configured-HIS transport (including direct SQL queries or other integrations) are not separate outbound entries, though their application API response can appear.

Data persist in api_exchange_logs, created idempotently at startup. Logging uses a bounded 1000-entry memory queue with approximately 2-second batch flush, 100 entries per batch. Storage failures preserve API behavior, retry the queue and show queue/drop/storage health in the viewer. Retention cleanup keeps roughly seven days / 50,000 rows, in bounded batches. Unflushed events can be lost on abrupt process termination. Historical request/response bodies from before this feature cannot be reconstructed.

Validation: build; release/unit tests; isolated PostgreSQL HTTP persistence, masking, permissions, filters/counts/pagination, correlation, self/auth exclusion and binary metadata; real local typed transport non-2xx metadata; Chromium desktop/tablet view, filter, detail, escaped JSON, copy, empty/error states and permission gating. Hospital production APIs and database were not accessed. No new installer or version was created for these pending changes.
