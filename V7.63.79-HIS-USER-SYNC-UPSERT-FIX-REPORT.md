# HealthCheck v7.63.79 – HIS User Sync Upsert Fix

## Scope
Fixes the Production HIS user synchronization failure caused by `duplicate key value violates unique constraint app_users_username_unique_idx`.

## Changes
- Normalize usernames with trim + case-insensitive matching before sync.
- Deduplicate duplicate usernames returned by HIS before touching HealthCheck state.
- Repair duplicate usernames already present in `app_state`, preferring LOCAL/admin accounts.
- Match existing accounts by normalized username first, then HIS user ID.
- Repeated HIS sync is idempotent: existing users are updated instead of re-created.
- Preserve LOCAL account password, active state, and manually assigned role.
- Apply HIS `lovcptypid` Role Mapping automatically only to non-LOCAL/HIS-managed accounts.
- Accounts without an active Role Mapping remain `UNMAPPED`; no role is guessed.
- Relational `app_users` mirror now reconciles by normalized username before ID upsert, preventing the unique-index collision even when legacy IDs differ.
- Sync summary now reports added, updated, skipped, duplicate HIS rows, repaired state duplicates and identity conflicts.
- Database failures return structured technical detail (`code`, `constraint`, `table`, detail) while retaining a user-readable message.

## Safety
- Production only (`APP_ENV=production`).
- Production port remains 3000.
- No HIS source data is modified.
- Existing LOCAL credentials are not replaced by HIS sync.
- Update Center root files remain present: `server.js`, `package.json`, `VERSION.txt`, `INSTALL-REPAIR.bat`.

## Verification
`npm run test:release` passed 9/9 tests, including:
- Production release identity and updater survival.
- Username normalization/deduplication.
- LOCAL role/credential preservation.
- Relational mirror username reconciliation.
- Sync result/error detail reporting.

## Recommended Production validation
1. Run Sync once with existing users present.
2. Run Sync a second time immediately; it should report updates/skips rather than duplicate-key failure.
3. Confirm a LOCAL user whose username also exists in HIS keeps their password, active state and manually assigned Role.
4. Confirm mapped HIS users receive the configured Role and unmapped users remain visibly unmapped.
